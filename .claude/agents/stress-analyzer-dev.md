You are working on a personal analytics tool that correlates Garmin Connect stress data with calendar events for a 9 AM–5 PM workday, centered on a "Leaderboard" of who stresses the user out the most. The user runs macOS, Python 3.14 (Homebrew). This IS a git repo (`git init` as of this project's second working session) — commit your work, don't leave it uncommitted.

## Layout

- `stress_core.py` — all shared logic, no blocking terminal I/O (no `input()`/`getpass()`). Config resolution, Garmin login, stress/sleep/Body Battery fetch, `.ics` parsing (including attendee extraction), minute-by-minute correlation, before-vs-during meeting stress delta, analytics, chart builders (matplotlib; Plotly may be added alongside for specific interactive dashboard charts — see below). Both the CLI and the dashboard import from here — keep it that way; don't duplicate logic into either entry point.
- `storage.py` — SQLite persistence (`~/.config/stress_analyzer/history.db`). Tables: `stress_minutes` (date, timestamp_local, stress, event), `event_summary` (date, event, avg_stress, peak_stress, minutes, delta_stress — the last column added via a migration, see gotcha below), `daily_summary` (date, overall_avg, overall_peak, computed_at), `event_attendees` (date, event, attendee_email, attendee_name), `daily_recovery` (date, sleep_score, total_sleep_minutes, body_battery_low, body_battery_high). `save_day()` deletes-then-inserts per date, so re-running a day is idempotent. `load_person_rollup()` is the Leaderboard's data source: minutes-weighted avg_stress, avg_delta, and total_stress_exposure (a cumulative, uncapped sum — not divided down to an average) per attendee.
- `stress_analyzer.py` — CLI entry point. Also what the launchd job runs unattended. Has `--setup` (one-time interactive config wizard), `--date`/`--output`/`--db`, and `--backfill-days N` (pre-load N days of history — e.g. before a live demo — skipping cached days and surviving per-day failures). Falls back to a clean `sys.exit` (not a hang) when required config is missing and stdin isn't a TTY.
- `dashboard.py` — Streamlit UI (`streamlit run dashboard.py`, localhost:8501). Tabs, in order: **🏆 Leaderboard** (the primary/default view — hero stat row, ranked table with Rank/Avg stress/Peak/Total exposure/Δ columns, a "Rank by" radio for which metric sorts it, minimum-meetings filter slider, chart in a collapsed expander), **Recovery** (sleep/Body Battery vs. stress correlation), **Daily Detail** (single day), **Trends** (date-range rollup). There is no sidebar — Settings is a `st.popover()` dropdown next to the title, top-right, not a permanent left sidebar (the user explicitly disliked the sidebar taking up screen width). There is no "Patterns" (day-of-week/hour) tab — it existed briefly and was explicitly removed at the user's request; don't reintroduce it unless asked. Uses `st.pyplot(fig, width="stretch")` for matplotlib charts — NOT the deprecated `use_container_width`.
- `com.joebruchalski.stressanalyzer.plist` — launchd job, daily 6:30 PM, staged in `~/Library/LaunchAgents/` but loading/unloading it is a persistent background action with real credential access — never `launchctl load`/`unload` it yourself without the user explicitly asking in that turn.

## Environment

Always `source .venv/bin/activate` (or invoke `.venv/bin/python3` directly) before running or testing anything — the system `python3` doesn't have the dependencies and will fail with `ModuleNotFoundError`. After changing `requirements.txt`, `pip install -r requirements.txt` inside the activated venv. If you're in a fresh git worktree, it has no `.venv` yet — create one.

The Streamlit dashboard, if left running in the background from a prior session, does NOT hot-reload on file changes (no `watchdog` installed) — after editing `stress_core.py`, `storage.py`, or `dashboard.py`, kill and restart it: `pkill -f "streamlit run dashboard.py"` then relaunch.

**Multi-agent workflow**: when asked to parallelize work across multiple agents, the harness's built-in `isolation: "worktree"` may fail with "not in a git repository" even though one exists (a stale environment snapshot from session start) — the fallback is manually running `git worktree add -b feature/x ../projects-wt-x` and pointing each agent at that absolute path directly in its prompt. Whoever does the integration merges each branch one at a time (not all at once), running the full test suite and an `AppTest` smoke check against real production data after each merge, before moving to the next — this caught real cross-branch conflicts (e.g. two branches both changing `run_analysis()`'s return signature) that a single combined merge would have made much harder to untangle.

## Hard-won gotchas — don't re-break these

1. **Never guess at a library's internals — inspect the installed version.** A prior guess at `garminconnect`'s API (`api.garth.dump(...)`) crashed with `AttributeError`. Use `python3 -c "import X, inspect; print(inspect.getsource(X.method))"` or `inspect.signature(...)` before writing code against any library method you haven't already seen used correctly in this codebase — this applies to `garminconnect` (`Garmin.login(tokenstore)` handles cached-token-first/fresh-login-fallback/persisting internally — don't add manual token logic), `streamlit` widgets (e.g. `st.popover`'s exact kwargs), and any new library (e.g. `plotly`) alike. Known `garminconnect` exceptions: `GarminConnectAuthenticationError`, `GarminConnectTooManyRequestsError`, `GarminConnectConnectionError`, `GarminConnectNotFoundError`, `GarminConnectInvalidFileFormatError`. Known real Garmin API shapes (found by live inspection, not docs): `get_sleep_data(cdate)` → `dailySleepDTO.sleepScores.overall.value` for sleep score, `dailySleepDTO.sleepTimeSeconds` for duration; `get_body_battery(startdate, enddate)` → a list of per-day dicts, each with `bodyBatteryValuesArray` (list of `[timestamp_ms, level]` pairs).
2. **Matplotlib's `DateFormatter` silently defaults to UTC**, even for tz-aware pandas Timestamps — it will *not* infer the data's timezone. Always pass `tz=` explicitly or times will render hours off with no error or warning.
3. **Matplotlib bar/scatter charts: `zorder=0` on `ax.grid()` alone does NOT reliably sit gridlines behind bar patches or scatter markers** (confirmed via minimal repro — it's a real, reproducible matplotlib quirk, not data-specific). Gridlines render visibly cutting through the marks. The actual fix is `ax.set_axisbelow(True)` before the `ax.grid(...)` call (drop the `zorder=0`). Line charts (`ax.plot`) are unaffected — only fill/patch-based marks. This bit every bar/scatter chart in this codebase at least once; check any new one visually, don't assume the old pattern was safe to copy.
4. **Credentials are never written to disk in plaintext.** Email/`.ics` path/tokenstore path/calendar-owner-email/internal-domain-filter live in `~/.config/stress_analyzer/config.json`; the Garmin password lives only in the macOS Keychain (service name `stress-analyzer-garmin`, via the `security` CLI). If you add new secrets, follow this pattern.
5. **Real credentials/session/database ARE reachable from a dev or agent context** (including from a git worktree — `~/.config/stress_analyzer/` is outside the repo, unaffected): `stress_core.resolve_config()` + `stress_core.garmin_login(...)` will reuse the cached session token and generally won't trigger a fresh rate-limited login. This is useful for confirming a real API response shape (e.g. discovering sleep/Body Battery field names) or backfilling derived data into the real DB from already-stored grids (no new Garmin call needed) — but Garmin has genuine IP-based rate limits this account has hit before, so make any live call count: 1-2 known-good dates, not a loop across many. Before running anything that WRITES to the real `history.db` (e.g. a schema migration), back it up first (`cp history.db history.db.bak-<reason>`) — cheap insurance for an otherwise-untested-in-production code path.
6. **Config resolution order** (see `resolve_config()`): env vars (`GARMIN_EMAIL`, `GARMIN_PASSWORD`, `ICS_FILE_PATH`, `GARMIN_TOKENSTORE`, `CALENDAR_EMAIL`, `INTERNAL_DOMAIN`) → saved config file/Keychain → caller fills gaps (CLI prompts interactively; dashboard shows the Settings popover form). Don't add a code path that calls `input()`/`getpass()` inside `stress_core.py` — that would break the dashboard and the automated job.
7. **Calendar input is a local `.ics` file, not a live feed** (deliberate choice — deferred: live private-ICS-URL sync, see memory). If the user reports stale calendar data in an automated run, that's expected until live sync is added, not a bug.
8. **Chart colors**: `stress_core.EVENT_COLORS` is a validated colorblind-safe categorical palette used in fixed order (from the `dataviz` skill's reference palette) — never cycle it, never reorder it arbitrarily, and fold anything past 8 concurrent event colors into `OVERFLOW_COLOR`. Magnitude/ranking charts (one measure across categories, e.g. the Leaderboard bar chart) use a single sequential hue (`STRESS_LINE_COLOR`) instead — color isn't carrying identity there, position/label already does. If asked to change chart styling meaningfully, load the `dataviz` skill first rather than picking colors by eye — this applies equally to any interactive (Plotly) charts, not just matplotlib.
9. **After any chart-code change, actually render it and look at it** before calling it done — several real bugs (the UTC/local time axis shift, the gridline-through-bars defect) were invisible in the code and only caught by rendering and inspecting the output. For matplotlib, save to PNG and `Read` it. For Plotly, `fig.write_image(...)` needs `kaleido` installed (fine as a temporary dev-only tool, don't add it to `requirements.txt` unless static export is actually a feature) — or fall back to reasoning carefully through the hovertemplate/layout code plus an `AppTest` no-exception check if a static render isn't practical.
10. **`build_daily_chart` (matplotlib) is used by BOTH the dashboard AND `stress_analyzer.py`'s CLI PNG export** — don't remove or change its return type; add a parallel function (e.g. `build_daily_chart_interactive`) for dashboard-only interactive versions instead. Other chart builders (e.g. `build_trend_chart`, `build_recovery_scatter_chart`) may only be used by the dashboard — grep for all call sites before assuming you can safely replace one in place.

## Testing approach used so far

- `python3 -m py_compile <file>.py` for a fast syntax check after edits.
- Synthetic-data round-trip tests for `storage.py` (build a fake minute-grid DataFrame, `save_day`, then read it back and diff) — including schema-migration tests that build a DB with the literal OLD schema first, to prove `init_db()`/`save_day()` migrate it in place without crashing or losing data.
- `streamlit.testing.v1.AppTest.from_file("dashboard.py")` to catch runtime exceptions in the dashboard without a real browser — check `at.exception` is empty, and inspect `dir(tab)` on a populated tab before assuming what element type a given `st.*` call shows up as in the AppTest tree (e.g. don't assume — check).
- Fake API stub classes (see `_FakeGarminApi` in `tests/test_stress_core.py`) for testing Garmin-fetch functions without a real network/login.
- Clean up any test artifacts you create (temp DB rows, Keychain test entries, background `streamlit` processes) before finishing — don't leave synthetic data sitting in the user's real `~/.config/stress_analyzer/history.db`.
